Resumen ejecutivo

1. Visión general del proyecto

AG Services requiere información contable clara, oportuna y trazable. El sistema desarrollado responde a esa necesidad mediante una SPA web conectada a una API REST en Flask y a una base de datos MySQL.

Problema
Información tardía, baja trazabilidad, dificultad para controlar movimientos, inventario y resultados.
Solución
Aplicación contable integrada con módulos operativos, seguridad por roles y almacenamiento persistente.
Resultado
Flujo real Navegador → Flask → SQLAlchemy → MySQL, validado mediante Network, terminal y Workbench.

1.1 Alcance funcional

Autenticación JWT y roles ADMIN y VENDEDOR.
Dashboard con indicadores financieros y últimos movimientos.
CRUD de ventas, gastos, inventario y catálogo de cuentas.
Reportes financieros construidos a partir de datos persistidos.

Fase 01

2. Gestión comercial y atención inicial

La iniciativa parte de una necesidad empresarial concreta: mejorar el control, oportunidad y confiabilidad de la información contable de AG Services y sus procesos operativos. En el análisis inicial se identificaron problemas de atraso de información, complejidad tributaria, ausencia de control presupuestario, poca supervisión y baja capacidad de proyección financiera.

2.1 Necesidad identificada

Información clara
Disponer de movimientos y saldos organizados para conocer la situación del negocio.
Control operativo
Registrar ventas, gastos e inventario en un sistema único y trazable.
Decisiones seguras
Convertir los registros transaccionales en dashboard y reportes útiles.
Seguridad
Diferenciar permisos entre administración y operación mediante roles.

2.2 Propuesta de valor tecnológica

La solución no pretende sustituir todas las funciones de un ERP contable empresarial. El alcance académico se concentra en demostrar una arquitectura Full Stack coherente y funcional para organizar, procesar, consultar y reportar información financiera básica de AG Services.

4.13 Diseño de seguridad

  • Las contraseñas se almacenan mediante hash.
  • El JWT contiene identidad, rol y expiración.
  • Los endpoints protegidos validan el token.
  • La autorización se aplica en backend; el frontend complementa la experiencia ocultando o bloqueando acciones.
  • CORS limita los orígenes permitidos para la SPA.
  • Las variables sensibles se separan del código mediante .env.

7.2 Flujo representativo: crear una venta

  1. El usuario autenticado diligencia el formulario en la SPA.
  2. JavaScript envía POST /api/v1/ventas con JSON y JWT.
  3. El controlador valida autenticación y recibe la solicitud.
  4. El DTO verifica los campos obligatorios.
  5. El servicio aplica reglas de negocio y calcula el total.
  6. El repositorio persiste el modelo mediante SQLAlchemy.
  7. MySQL almacena el registro.
  8. La API responde con HTTP 201 y JSON.
  9. El frontend actualiza la tabla y el dashboard.

Evaluación arquitectónica

8. Rendimiento, escalabilidad, disponibilidad, costos y riesgos

8.1 Rendimiento

Para el alcance académico y volumen esperado, Flask y MySQL ofrecen capacidad suficiente. Las operaciones son CRUD sencillas y los reportes se apoyan en consultas de base de datos. Para volúmenes mayores sería recomendable incorporar paginación, índices adicionales, caching y análisis de consultas.

8.2 Escalabilidad

El monolito modular permite escalar verticalmente y, posteriormente, ejecutar varias instancias del backend detrás de un balanceador. La separación por dominios reduce el costo de extraer un módulo a servicio independiente si el crecimiento lo justificara.

8.3 Disponibilidad

La versión actual es local y no implementa alta disponibilidad. En producción se requerirían servicios administrados o redundantes, reinicio automático, copias de seguridad, monitoreo y health checks.

8.4 Costos

La arquitectura evita costos innecesarios de microservicios para el alcance actual. Flask, MySQL, Tailwind, Git y las principales librerías empleadas son de uso abierto. El costo productivo dependería del hosting, base de datos, dominios, copias de seguridad y observabilidad.

8.5 Riesgos principales

Cierre

11. Conclusiones

El Sistema Contable AG Services cumple el objetivo de integrar una interfaz SPA, una API REST modular y una base de datos relacional dentro de una arquitectura coherente y demostrable. El proyecto permite recorrer una funcionalidad desde la interacción del usuario hasta la persistencia en MySQL, manteniendo separación de responsabilidades, validación, autorización y trazabilidad.

La elección de un monolito modular fue adecuada para el alcance: preserva simplicidad de despliegue sin renunciar a dominios y capas bien definidos. La autenticación JWT y la autorización por roles fortalecen la seguridad, mientras que SQLAlchemy y Flask-Migrate proporcionan una base consistente para la evolución del modelo de datos.

Como evolución futura se recomienda desplegar los servicios en infraestructura permanente, introducir pruebas automatizadas más amplias, paginación, observabilidad, copias de seguridad y mecanismos de alta disponibilidad según el crecimiento del sistema.

Estado de la versión documentada: integración Frontend–Backend–MySQL funcional, roles ADMIN/VENDEDOR, CRUD principales, dashboard, reportes, documentación arquitectónica y evidencias de ejecución.
